# 判断⑨：日記のバージョニング（編集履歴）— 案A

日付: 2026-05-30
ステータス: 設計確定 / 実装は未着手
関連: 設計仕様書 2-1(Raw層の不変性), 7-3(Raw不変性保証)

---

## 解きたいこと

日記を途中まで書いて、後で「書き直したい」(特にタイポ修正)。
ただし **編集履歴を残したい**(gitのcommitのように、いつ何を書いたかを遡れる)。

## 根本にある制約（最重要）

Raw層の大原則 = **「不変・改変しない・真実の記録」**(仕様書2-1 / 原則的にUPDATE/DELETEしない)。
→ 「contentを上書きする」素朴な編集は、この原則を破る。やってはいけない。
→ 解決策は「上書き」ではなく「**版を積む**」。過去を消さず、新しい版を追加する。
   これはgitが過去コミットを消さず積み上げるのと同じで、原則と完全に一致する。

## 採用案：案A（バージョニング / 版を丸ごと保存）

タイポ含め過去の文も直したいので、追記のみの案Bではなく、版ごと丸ごと保存する案Aを採用。

### 保存方式：A-2（最新版は本テーブル / 過去版は別テーブル）

```
編集前: v1 (元の日記, hash=h1)
  ↓ タイポ修正して保存
編集後:
  raw_entries          → 最新版 v2 (修正済み, hash=h2)  ← 普段表示するのはこれ
  raw_entry_versions   → v1 (元の記録, hash=h1) を履歴として保存
  ChromaDB             → v2の内容で上書き登録(検索は常に最新版基準)
```

役割分担:
- raw_entries        = 「今の真実(最新版)」
- raw_entry_versions = 「過去の版の履歴倉庫」(消さない = Raw不変性はここで担保)

### 新テーブル案：raw_entry_versions

| カラム | 型 | 説明 |
|---|---|---|
| version_id | TEXT PK | 例 20220217-084400-diary#v1 |
| entry_id | TEXT | 元エントリのid(raw_entries.id を参照) |
| version_no | INTEGER | 版番号 1,2,3... |
| content | TEXT | その版の本文 |
| hash | TEXT | その版の SHA-256(entry_id+date+content) |
| edited_at | DATETIME | その版が作られた日時 |

- 編集が起きる前の現行版を、このテーブルに退避してから raw_entries を新版に更新する。
- 「履歴を見る」= entry_id で raw_entry_versions を時系列に並べる(gitのlog相当)。

## 実装時に必ずやること（忘れると壊れる）

1. **ハッシュは版ごとに再計算**: content が変わるので hash も新しく計算。
   各版に「その時点で確かにこう書かれた」証明が残る → むしろ信頼性が上がる。
2. **ChromaDBの再ベクトル化**: 編集したら最新版でベクトルを取り直す(古い本文のままだと検索がズレる)。
   ChromaDBは同じidで add すると上書きされるので、最新版で add し直せばよい。
   (= 保存時の自動登録の延長。更新時は上書き登録)
3. **元エントリは絶対にDELETEしない**: 更新でも、旧版は raw_entry_versions に必ず退避してから。

## UI（実装イメージ）

- 閲覧画面(/entry/[id])に「編集」ボタン → 現在の内容が入った状態で書く画面を開く →
  直して保存 → 新版になる(旧版は履歴へ)。
- 「履歴」ボタン → 過去の版を時系列表示(gitのlogのように)。各版の edited_at と本文が見える。
  = 当初要望の「追加記入履歴を残したい」がここに当たる。

## 規模感

DBにテーブル追加 + 編集API + 履歴API + 編集/履歴UI + 更新時のベクトル再登録。
第二層(AI対話)と並ぶ「次にやる大きめテーマ」。小さくはない。

## 補足：なぜ差分保存(A-3)にしないか
gitの内部は差分だが、個人の日記は版がそう何十個もできない想定なので、
版を丸ごと持つA-2で十分シンプル。差分管理の複雑さは今は不要。
「生データを持っておけば後から変えられる」(原則4)ので、まず丸ごと保存で始める。
